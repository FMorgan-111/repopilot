## 🎯 三个主打故事(按"含金量"排序,优先讲这几个)

### ★1. httpx 的 timeout 根本不限制请求总时长(最硬核,首选)

**难点:** 配置里写了 `timeout=60`,但一次成功的 LLM 调用实测跑了 **142.7 秒**,完全没被拦住。phase 级超时(180s)成了唯一兜底。

**怎么发现的:** 我没有直接猜,而是去看 trace 里每次 LLM 调用的 `elapsed_seconds` 和 `response_tokens`。算了一下吞吐:
```
725 tok / 25.7s  = 29 tok/s
1022 tok / 48.2s = 21 tok/s
1194 tok / 142.7s = 8.4 tok/s   ← 平滑退化的同一条曲线
```
吞吐从 29 平滑掉到 8.4 tok/s——如果是"超时+重试拼出来的",曲线不会这么平滑。说明是**单次生成,端点在涓流吐字节**。

**根因:** `httpx` 的 `timeout=60`(裸 float)会展开成 connect/read/write/pool **四个各自独立**的超时,其中 read 是"两次收到字节之间的最大间隔",**不是整个请求的墙钟时间**。只要端点持续涓流,read 超时永远被重置。**httpx 在设计上就没有"整个请求最多 N 秒"这个选项。**

**修复:** 用 `asyncio.wait_for` 在外层包一个真正的墙钟硬上限(200s)。关键设计:超时抛 `asyncio.TimeoutError`,而它**不在**我的重试白名单里(白名单只认 `httpx.TimeoutException`/502/503/网络错误)——所以**慢生成快速失败不重试,瞬态错误仍重试**。一举两得。

**权衡:** 200s 是"容忍慢尾、宁可多等拿结果",而不是"快速失败省成本"。因为现阶段首要目标是先跑通一次端到端。

> 面试加分点:这题展示了对 HTTP 客户端内部机制的理解(per-operation vs total timeout)、用数据证伪、以及"哪个异常该重试"的精细设计。

### ★2. 调试方法论:用数据推翻自己的假设(展示科学调试)

**场景:** 上下文改大后 plan 阶段超时了。我的第一反应是"prompt 太大了"。

**但我先验证再下结论:** 看 token 数——prompt 从 5668 涨到 6128 只 **+8%**,耗时却从 25s 涨到 142s,**+468%**。8% 的输入增长不可能造成 5.7 倍耗时。**我自己的假设被自己的数据推翻了。** 真正原因是端点延迟方差(见故事1)。

**为什么这个故事值钱:** 面试官问"你怎么调难 bug"时,这就是标准答案——**先形成假设,再用数据证伪,而不是顺着第一直觉改代码**。我在这个项目里反复用这个模式:每次失败先读 trace、算指标、证伪,再动手。

### ★3. 上下文饥饿的级联:失败点一直在移动(展示系统思维 + 韧性)

**难点:** 同一个失败信息"context collection made no progress"出现了 4 次,但**每次根因都不同**。这是最考验系统思维的部分——表象相同,病灶在移动。

**逐层剥开:**
1. **死循环**:规划器反复"要更多上下文",但 locate 只用 issue 原文搜索,每轮拿回同一批文件 → 加签名检测 + 硬上限刹车。
2. **locate 不听话**:规划器点名了 `runner.py`,locate 不消费 → 改成读规划器 `next_checks` 里的路径。
3. **规划器是瞎的**:它只看到文件**前 3%**(import 区),看不到函数体 → 上下文上限 1200→6000 字符。**这次第一次跑到了 execute。**
4. **locate 无状态丢上下文**:中途找到的好文件,在决定轮被丢弃(规划器写了残缺路径,读失败回退到垃圾)→ 改成跨轮累积。
5. **文档污染**:累积放大了 BM25 偏好,11 万字符的 `.rst` 文档霸占了喂给规划器的 top-4,源码被挤出去 → 排除文档类文件。
6. **规划器不肯收敛**:终于喂的是干净源码了,但它**每轮把假设推倒重来**(假设 ID 每轮全换),攒不出交补丁的信念 → 给 prompt 加"上下文收集压力",轮次越多越逼它交补丁。

**最关键的认知:** 修到第 6 层时我意识到——**问题已经从"基础设施"转移到"模型推理本身"了**。前 5 个是确定性的工程 bug(能写测试复现),第 6 个是 LLM 的非确定性推理质量,得用 prompt 工程 + 结构性兜底来治,是完全不同的方向。能区分这两类问题,是这个故事的价值。

> 面试加分点:"我以为修好了,但失败只是移到了下一层"——这种诚实的级联叙事,比"我一次就搞定了"可信得多,且展示了不放弃 + 分层定位的能力。

## 补充故事(被追问时用)

### 非确定性 eval 的陷阱
有一次运行(`1d718ae9`)确实跑到了 execute、补丁成功 apply。但我**没有宣布胜利**——因为同样的代码重跑 3 次再没复现。我把它如实记为"非确定性侥幸"。**LLM agent 的评测必须考虑非确定性,单次成功不等于能力。** 这点科学严谨性面试官会认。

### 死循环刹车的设计
不是简单加个计数器。用了两层:(a) `last_locate_signature`——把定位到的文件路径排序成指纹,相同则判定无进展提前停;(b) 硬上限 3 轮兜底。签名检测能更早止血,硬上限防止签名一直变化时的兜底失效。

---

## 架构一句话(被问"整体怎么设计的")

LangGraph 状态机:`UNDERSTAND → LOCATE → PLAN → EXECUTE → VERIFY → COMMIT`,失败走 `REFLECT → PLAN` 重试。每个阶段产出一个 **DecisionFrame**(结构化的假设/证据/下一步/推荐动作),路由是纯函数 `route_from_state` 读 frame 决定走向,不藏在 prompt 里。整个 run 是一个 Pydantic `AgentState`,可序列化、可 replay。这套"决策可观测"是和 Devin/Sweep 这类黑盒的主要差异。
